# 《心理学空间·自我探索Agent Pro》轻量服务器部署与运维方案

## 1. 目标

本文面向当前真实环境：

- 腾讯云轻量应用服务器
- 服务器已安装 `git`、`docker`
- 资源紧张
- 希望一键部署、一键更新、可看动态日志、自动归档日志、自动清理空间、服务崩溃可邮件预警

本文给出两层方案：

- **P0 当前可落地方案**：`Docker Compose`
- **P1 演进方案**：`k3s / TKE`

当前推荐优先级非常明确：

- 先把 `Docker Compose` 单机方案打磨到稳
- 暂不在轻量服务器上直接上完整 K8s 控制面

---

## 2. 部署结论

## 2.1 P0 正式方案

- 单机 `Docker Compose`
- `nginx / caddy` 反向代理
- Java 服务 + Node 服务 + PostgreSQL + Qdrant + Redis
- 日志走 Docker stdout/stderr + 宿主机归档脚本
- 监控告警走轻量脚本 + 邮件通知

## 2.2 P1 演进方案

- 单机 `k3s`
- 若后续迁入腾讯云容器环境，再升级到 `TKE`

## 2.3 为什么当前不推荐直接上完整 K8s

因为你现在的机器条件是：

- 轻量应用服务器
- 资源紧张
- 目标先是稳定上线而不是集群炫技

在这种条件下，完整 K8s 会带来额外损耗：

- 控制面占资源
- 排障复杂度明显提升
- 日志与持久化管理更重

所以当前最合理路线是：

- `Compose` 先稳定
- 保持目录结构、镜像规范、配置规范与未来 K8s 对齐

---

## 3. 推荐运行拓扑

```text
server
├── reverse-proxy
├── phyok-java-gateway
├── phyok-java-auth
├── phyok-java-orchestrator
├── phyok-java-memory
├── phyok-java-billing
├── phyok-java-audit
├── phyok-java-admin
├── phyok-node-capability
├── postgres
├── qdrant
├── redis
└── logrotate + backup + alert scripts
```

说明：

- 当前单机环境下，不建议把每个 Java 微服务都拆成完全独立容器再无限横向扩容
- P0 阶段可以合并部分低频服务，避免容器过多

推荐合并策略：

- `auth-service + billing-service + audit-service + privacy-service` 可先合并为一个 `core-admin-api`
- `memory-service + knowledge-service` 可视压测情况决定是否合并

## 4. 一键部署规范

## 4.1 推荐目录

```text
/opt/phyok/
  releases/
  shared/
    env/
    logs/
    backups/
    data/
      postgres/
      qdrant/
      redis/
      cos-cache/
  scripts/
    deploy.sh
    update.sh
    logs.sh
    cleanup.sh
    healthcheck.sh
    alert.sh
  compose/
    docker-compose.prod.yml
```

## 4.2 一键部署脚本目标

### `deploy.sh`

职责：

- 拉代码
- 检查 `.env`
- 构建镜像
- 启动 compose
- 做健康检查
- 输出访问地址与日志命令

### `update.sh`

职责：

- `git pull`
- 重新构建变化镜像
- 滚动重启 Compose 服务
- 健康检查失败则回滚到上一版镜像标签

### `logs.sh`

职责：

- `tail -f` 查看核心服务日志
- 支持按服务名过滤

### `cleanup.sh`

职责：

- 清理旧镜像
- 清理无用容器
- 清理超期日志归档
- 清理过期备份

---

## 5. Docker 规范

## 5.1 镜像规范

- Java 服务统一多阶段构建
- Node 服务独立 runtime 镜像
- 所有镜像必须固定 tag，不允许只用 `latest`

建议 tag：

- `release-YYYYMMDD-HHmm`
- `git-sha`

## 5.2 容器限制

资源紧张环境必须显式限制：

- CPU
- Memory
- restart policy
- healthcheck

建议：

- `postgres`：优先保证内存
- `qdrant`：严格控制 payload 与 collection 体量
- `node-capability-service`：限制并发，避免 FFmpeg/ASR 挤爆机器
- `java`：明确 `Xms/Xmx`

---

## 6. K8s / k3s 规划

## 6.1 现在怎么做

- 当前机器先不强制上 K8s
- 只要求部署资产按未来 K8s 兼容方式组织：
  - `deploy/docker`
  - `deploy/k8s`
  - `deploy/helm`

## 6.2 后续怎么升

### 单机升级

- 从 `docker-compose` 迁移到 `k3s`

### 云上升级

- 从 `k3s` 迁移到 `TKE`

## 6.3 k8s 重点对象

- `Deployment`：Java / Node 无状态服务
- `StatefulSet`：PostgreSQL、Qdrant
- `PVC`：数据库与向量库持久卷
- `Ingress / Gateway`：统一入口
- `CronJob`：日志归档、备份、清理

---

## 7. 日志方案

## 7.1 运行期日志

当前推荐：

- 应用日志全部输出到 stdout/stderr
- 使用 `docker logs -f` 实时查看
- 同时将关键服务日志归档到宿主机目录

## 7.2 动态日志查看

推荐命令封装：

```bash
./scripts/logs.sh gateway
./scripts/logs.sh java
./scripts/logs.sh node
./scripts/logs.sh postgres
```

## 7.3 日志归档

建议：

- 按天归档
- gzip 压缩
- 保留 7~15 天
- 审计类日志额外落 PostgreSQL，不只依赖容器日志

---

## 8. 空间治理

资源紧张时，最容易把服务器拖死的是：

- Docker 镜像残留
- 旧日志
- Qdrant 数据增长
- PostgreSQL WAL / 备份积压
- FFmpeg 与上传临时文件

## 8.1 必做清理项

- Docker dangling images
- 历史 release 包
- `/tmp` 媒体临时文件
- 过期日志归档
- 过期数据库备份

## 8.2 Qdrant 控制点

- payload 严格保持轻量
- 只保留必要 collection
- 删除无用实验索引
- 定期 snapshot 再清理旧 snapshot

## 8.3 PostgreSQL 控制点

- 大表按月分区
- 审计表、token 表定期归档
- vacuum / analyze 定期执行

---

## 9. 崩溃预警与邮件通知

## 9.1 告警方式

P0 使用轻量脚本就足够：

- 服务健康检查失败
- 容器退出
- 磁盘超过阈值
- 内存持续高位
- CPU 持续高位

触发后发送邮件到：

- `simon.wzb@qq.com`

## 9.2 推荐告警阈值

- 磁盘使用率 > `80%`
- 内存使用率 > `85%`
- CPU 持续 5 分钟 > `90%`
- Qdrant / PostgreSQL / Gateway 健康检查失败

## 9.3 邮件通道

优先复用：

- 腾讯云 SES

告警脚本可使用：

- `curl + SMTP API`
- 或 Java/Node 内置邮件服务接口

---

## 10. 备份策略

## 10.1 PostgreSQL

- 每日全量备份
- 每小时增量/WAL 策略按成本选配
- 保留最近 7 天本地备份
- 每日同步一份到 COS

## 10.2 Qdrant

- 每日 snapshot
- 与 PG 版本号对齐
- snapshot 上传到 COS

## 10.3 配置与 Secrets

- `.env` 不进仓库
- 定期备份非敏感配置模板
- 敏感参数通过服务器本地 secret 文件管理

---

## 11. 健康检查

每个服务都必须有：

- `/health/liveness`
- `/health/readiness`

P0 最低要求：

- Gateway
- Java Core API
- Node Capability
- PostgreSQL
- Redis
- Qdrant

---

## 12. 生产建议

## 12.1 当前正式建议

- 先用 `Docker Compose`
- 预留 `k3s / TKE` 资产目录
- 控制服务数
- 控制日志量
- 控制向量体量
- 控制磁盘增长

## 12.2 不建议

- 轻量服务器直接上完整多节点 K8s
- 初期就把所有服务拆得过细
- 把所有日志长期明文保存在本地磁盘
- 让媒体临时文件无限堆积

---

## 13. 一句话结论

当前环境下最正确的方案不是“先把 K8s 搭满”，而是：

- 用 `Docker Compose` 把单机生产能力打磨稳定
- 用脚本补齐一键部署、滚动更新、日志、归档、清理、告警
- 结构上为未来 `k3s / TKE` 保留升级路径
