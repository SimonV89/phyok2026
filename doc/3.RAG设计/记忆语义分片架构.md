# 《心理学空间·自我探索Agent Pro》记忆语义分片架构说明

## 1. 文档目标

本文专门定义“自然语义分片”在新系统中的正式实现方式。

本轮架构结论已经明确：

- 分片质量优先
- 自然语义分片采用 `LLM API`
- embedding 模型与分片模型分离

本文回答 4 个核心问题：

- 为什么分片要交给大模型 API
- 大模型 API 到底负责什么
- 服务端如何约束与校验 LLM 输出
- 分片结果如何进入 `PG + Qdrant` 检索链路

---

## 2. 一句话结论

自然语义分片的正式实现采用：

```text
标准化文本
-> semantic-chunk-service
-> LLM API 结构化分片
-> schema 校验
-> token 边界修正
-> PG 入库
-> embedding
-> Qdrant
```

其中：

- `LLM API` 负责“按心理语义边界切分”
- `bge-m3` 负责“把切好的 chunk 向量化”

---

## 3. 为什么这里要用大模型 API

因为你的场景不是普通文档切片，而是心理叙事切片。

用户输入常常同时包含：

- 时间跳跃
- 情绪转折
- 关系模式
- 原生家庭片段
- 当下困扰
- 隐含自我判断

这类文本如果只靠：

- 固定 token 切块
- 固定句号切块
- 纯规则切块

很容易出现：

- 一个 chunk 混进多个事件
- 一个情绪被硬切断
- 童年与当下混成一块
- 关系模式和具体事件粘在一起

所以这里的正确策略不是“先压成本”，而是“先把分片质量做对”。

---

## 4. LLM API 在这里的职责

大模型 API 只负责：

- 判断语义边界
- 判断哪些句子应合并成一个 chunk
- 生成结构化 chunk 列表
- 为 chunk 输出基本标签

大模型 API 不负责：

- 直接写库
- 直接做 embedding
- 直接检索
- 直接决定最终排序

也就是说：

- 大模型只回答“怎么切”
- embedding 模型只回答“怎么比”

---

## 5. 推荐输出结构

建议 `semantic-chunk-service` 要求 LLM API 输出严格 JSON：

```json
{
  "chunks": [
    {
      "seq": 1,
      "content": "小时候母亲生气时会几天不理我。",
      "fragmentType": "EVENT",
      "timelineRoot": "CHILDHOOD",
      "topicTags": ["原生家庭", "被忽视"],
      "emotionTags": ["害怕", "不安"],
      "confidence": 0.91
    }
  ]
}
```

服务端必须要求：

- 不能输出自然语言解释段落
- 不能输出非 JSON 杂质
- 不能输出缺字段对象

---

## 6. 服务端校验层

LLM API 不是直接可信写入器。

必须在 Java 服务端做二次校验：

## 6.1 Schema 校验

检查：

- JSON 是否合法
- `chunks` 是否存在
- 每个 chunk 必填字段是否完整
- `fragmentType` 是否在枚举内
- `timelineRoot` 是否在五根节点内

## 6.2 长度校验

检查：

- 单个 chunk 是否过短
- 单个 chunk 是否过长
- 单轮 chunk 数量是否异常

建议：

- chunk 目标区间：`220~420 tokens`
- 过长则触发二次切分修正
- 过短则尝试与相邻 chunk 合并

## 6.3 边界校验

检查：

- chunk 是否把句子切在奇怪位置
- 时间线是否明显冲突
- 人物关系是否无故中断

## 6.4 兜底策略

如果 LLM 输出失败：

- 允许重试
- 记录 `memory_chunk_job`
- 标记失败原因

不建议：

- 直接跳过校验
- 直接用粗糙硬切结果写正式主表

---

## 7. 与 embedding 的分工

## 7.1 分片模型

职责：

- 切块
- 判断语义边界
- 输出 chunk 结构

推荐：

- 外部 `LLM API`

## 7.2 embedding 模型

职责：

- 对已经切好的 chunk 做向量化

推荐：

- `BAAI/bge-m3`

## 7.3 为什么不能混成一个

因为两者处理的问题不同：

- 分片模型关注文本结构与意义边界
- embedding 模型关注语义表示与相似度比较

把二者混成一个职责，会导致：

- 工程难调
- 效果难复盘
- 成本难拆账

---

## 8. 在 Java 服务里的落地方式

## 8.1 服务拆分

推荐新增：

- `semantic-chunk-service`

## 8.2 调用关系

### 记忆入库链路

```text
agent-orchestrator-service
-> memory-service
-> semantic-chunk-service
-> LLM API
-> memory-service
-> PostgreSQL
-> MQ
-> embedding-worker
-> Qdrant
```

### 文档入库链路

```text
knowledge-service
-> semantic-chunk-service
-> LLM API
-> knowledge-service
-> PostgreSQL
-> MQ
-> embedding-worker
-> Qdrant
```

---

## 9. 表字段要求

`memory_fragment` 建议带：

- `chunk_confidence`
- `chunk_strategy`

`knowledge_chunk` 建议带：

- `chunk_confidence`
- `chunk_strategy`

`memory_chunk_job` 建议带：

- `llm_provider`
- `llm_model`
- `job_status`
- `retry_count`
- `last_error`

---

## 10. 成本与性能建议

你已经明确：

- 效果优先

所以当前策略是合理的：

- 默认走 `LLM API`

但工程上仍建议做两点：

## 10.1 异步化

- 分片走任务化
- 避免阻塞主链路太久

## 10.2 可重放

- 保留原始文本
- 保留 LLM 模型信息
- 保留失败原因

这样后续才能：

- 重切
- 回放
- 比较不同模型效果

---

## 11. 最终结论

《心理学空间·自我探索Agent Pro》的自然语义分片正式方案为：

- 使用 `LLM API`
- 服务端严格 schema 校验
- 与 `bge-m3` embedding 职责分离
- 通过 `semantic-chunk-service` 收口

这是当前“效果优先”前提下最合适的工程路线。
